# Large files in Beam

Use the new Beam on both devices. For transfers above 128 MiB, Beam reads the source file in 1 MiB slices to calculate SHA-256, then loads individual RaptorQ source blocks as needed. It skips whole-file gzip. The same source file needs to remain readable and unchanged during the transfer. The existing memory/download path remains for smaller files.

For a large file, open the receiver in desktop Chrome or Edge on localhost or HTTPS. Start camera or screen capture and let it see the file information. Click **Choose save location**, then resume scanning. You can choose the destination while the sender is still showing the file information, before starting the animated signal. When the transfer finishes, Beam checks the staged file against the sender's SHA-256, then saves automatically. A failed final save lets you pick another location without rescanning. Progress reaches 100% after the destination write closes successfully.

Beam puts completed blocks at their byte offsets in private browser storage (OPFS). At most 16 unfinished RaptorQ blocks remain active in RAM; unfinished blocks outside that window are staged as packets and reloaded when needed. Large-file repairs are sent block by block for efficient disk access. The sender caches no more than 32 MiB of source blocks' worth of RaptorQ encoders, plus one raw block. It retains the existing B3 packet format with an optional disk hint. Older receivers do not implement disk staging. Legacy oversized compressed transfers must be prepared again by the updated sender.

Allow for browser storage quota and approximately twice the file size in free space when staging and saving share a disk. The browser needs enough origin quota to stage the payload; having free OS disk space does not guarantee an adequate browser quota. Partial blocks are removed once written successfully and restored, and staged data is removed on Clear or successful save. Abandoned staging from closed pages is removed when another large transfer starts; active tabs hold an exclusive Web Lock. Closing or reloading Beam does not resume a transfer. Save dialogs may create an empty placeholder file; Beam writes payload bytes only after successful verification.

The native QR transfer rate still determines the transfer duration. This change removes the whole-file memory bottleneck and does not increase the optical rate.

Run the standard tests with `npm test`. `npm run test:large` exercises 129 MiB with real disk staging through a Node filesystem adapter. `npm run test:disk-browser` runs a real Chromium/OPFS compatibility check using a test file handle in place of the native save picker. With `BEAM_SPARSE_FILE` and optionally `BEAM_SPARSE_SHA256`, it can also run the sender/worker against a 24 GiB + 17 byte sparse fixture whose last bytes are 1 through 17. The browser test requires Playwright and Chromium as development dependencies only. Set `BEAM_CHROME_EXECUTABLE` if Chromium is not at `/usr/bin/chromium`.

Release checks: Chromium prepared a real 24 GiB + 17 byte sparse file from a native file input, matched the full SHA-256 from sha256sum, and generated correct original and repair packets for source block 24,576. Chromium also received and verified 6,684,699 bytes in actual OPFS with out-of-order blocks, disk spill and missing originals. The 129 MiB + 17 byte filesystem-adapter test fully decoded, verified and byte-compared the file at 30% seeded packet loss. These are separate checks; a complete 24 GiB optical transfer and the native save dialog were not exercised.
